knowledgelayer runbook

A step-by-step guide to keeping a knowledge layer beside a reproducible analytical pipeline: who holds which project, what connects to what, and how each review decision was made.

1. Install, and what IT needs

The source is public at github.com/philippa-mk/knowledgelayer, so IT can read all of it before anything is downloaded. Download knowledgelayer_0.2.0.tar.gz from the repository's Releases page and, once it is approved, in R:

install.packages("knowledgelayer_0.2.0.tar.gz", repos = NULL, type = "source")
library(knowledgelayer)

Use the full path to the file if it is not in your working directory.

2. Set up the knowledge folder

Pick a folder the team can reach, such as a shared drive or the root of an RStudio project, and create the layer there once:

kl_init("S:/Analytics")
options(knowledgelayer.path = "S:/Analytics")

This creates knowledge/, holding a project registry, the links between projects, a board, an append-only decision log and a handoffs/ folder. Every file is plain text. Put the options() line in your .Rprofile so you never pass the folder again.

3. Register projects and links

One entry per piece of work. Write down, while it is fresh, what a colleague would need if you were out tomorrow.

kl_add_project("annual-2026", "Annual performance report 2026",
               owner = "Your Name",
               sources = c("Case management extract", "Complaint intake records"),
               methods = "targets pipeline",
               location = "S:/Analytics/annual-2026")

kl_add_project("annual-2025", "Annual performance report 2025",
               owner = "Your Name", status = "done")
kl_link("annual-2026", "annual-2025", "reuses-code-from")
kl_find("complaint")     # has anyone here already worked with this?

Links are what make it a knowledge layer rather than a list: they show which projects share code, data or a method, so a change in one is checked against the others.

4. Describe work with the shared vocabulary

Two people rarely describe the same work in the same words. The package ships a shared vocabulary for oversight work (audit concepts, report types, kinds of criteria, a typology of findings and the broad program areas), so that work tagged with the same concept is found whatever words it uses.

kl_vocab("findings_typology")             # browse it
kl_resolve(c("separation of duties", "snow plowing"))
kl_add_project("vendors-2026", "Vendor payments review", owner = "Your Name",
               concepts = c("procurement and contracting", "duplicate payment"))
kl_find("contracting")                   # finds it through the synonym

kl_resolve() never guesses. A term that matches nothing says no concept; a term that matches more than one concept says ambiguous and lists them, and you choose with scheme =. Tags store short ids such as ft:improper-payments, never web addresses.

Add your office's own terms

The shipped clusters and program areas are starters: meant to be broadly applicable, but they may not fit your office perfectly. Some are typically run by states or counties; if your office does not oversee them, ignore them.

Your program areas, agencies and house terms go in a local layer, knowledge/vocabulary.json, which sits over the shipped vocabulary and never changes it. Program areas can come straight from a spreadsheet with the columns id, prefLabel, altLabels and broader:

kl_vocab_import("program-areas.csv")       # every broader must exist, or nothing is imported
kl_vocab_extend("agencies", "agency:streets", "Department of Streets", altLabels = "Streets")
kl_vocab_check()                          # dangling ids, cycles, duplicate labels

A finding can carry its kind, with typology = in kl_findings(). The review page then shows the kind and its links to the standards. Each link says how precise it is: a link to an exact principle says so, and a link to a whole standard says link to the whole standard, not to this point. To load the vocabulary into a linked-data tool, export it with kl_export_skos("vocab.ttl", base = "https://your.domain/vocab/"): you choose the web address, and there is no default. The vignette vignette("example-city", package = "knowledgelayer") walks through all of it with an invented city.

5. Find single points of knowledge

kl_single_points()       # live projects only one person can run
kl_handoff("annual-2026")  # drafts a handoff note in knowledge/handoffs/

The handoff is pre-filled from the registry, links, decision log and board, and marks what only the author can add. The section that matters most is decisions and why: what was done is easy to rebuild, why it was done is what gets lost.

The test of a good handoff: could someone new, reading only this note, make the right next move without asking anything?

6. Keep a project board

Three short lists per project: Inbox (new, unsorted), Roadmap (decided, with a status) and Parking lot (good, not now). Nothing reaches the Roadmap until a person triages it.

i <- kl_inbox("Add district-level rates", "annual-2026", by = "Supervisor")
kl_triage(i, "TAKE", by = "Your Name")
kl_roadmap_status(i, "done", checked = "matches WP-7 totals")
kl_board("annual-2026")

Triage choices are TAKE (onto the Roadmap), HOLD (park it), DROP (let it go, and log why) and DISCUSS (leave it for now). "Done" needs a note on how you know it works.

7. Run a review end to end

The author

  1. Gather findings from your independent-review template, and from reading the report as its harshest reader would: kl_review_angles() lists seven angles.
  2. Record each finding with a severity, a proposed fix and the verdict you would stand behind. You cannot propose TWEAK: that one is the reviewer's. 
    findings <- kl_findings(
  id = c("F1", "F2"),
  finding = c("312 records appear twice after the address join",
              "Chart 3 labels the 2025 series as 2024"),
  severity = c("high", "low"),
  proposed_fix = c("Deduplicate on record id", "Fix the label"))
kl_write_findings(findings, "qa/findings.csv")
  3. Build the review page and email it to the reviewer: 
    kl_review_page(findings, "qa/REVIEW_annual-2026.html",
               review_id = "annual-2026-qa", author = "Your Name",
               return_to = "Your Name (you@example.org)")

The reviewer (no R needed)

  1. Save the attached page, then open the saved file in Edge, Chrome or Firefox. It will not work in an email preview.
  2. For each finding, keep or change the preselected verdict, and add a note wherever the reasoning should be on record. TWEAK and MERGE need a note.
  3. Enter your name and click Export decisions. Send the downloaded APPROVED_…json file back to the author. Work in progress is saved in the browser, so it is safe to close and come back.

Back with the author

v <- kl_read_verdicts(kl_newest_verdicts("qa", review = "annual-2026-qa"))
kl_rubber_stamp_check(v, kl_read_findings("qa/findings.csv"))

The check fails an export that leaves a finding undecided, was made on findings that have since changed, or has a TWEAK or MERGE without a note. It warns on the marks of a sign-off rather than a review: every proposal accepted with no notes, findings never on screen long enough to read, a high-severity finding with no comment, or an author reviewing their own work. The page tells the reviewer that time on screen is recorded.

8. Gate the pipeline on the review

In _targets.R, make the report depend on the gate, so it cannot build until the review is in and has passed:

tar_option_set(packages = "knowledgelayer")

list(
  tar_target(findings_file, "qa/findings.csv", format = "file"),
  tar_target(findings, kl_read_findings(findings_file)),
  tar_target(verdict_file, kl_newest_verdicts("qa", review = "annual-2026-qa"), format = "file"),
  tar_target(cleared, kl_gate(verdict_file, findings)),
  tar_target(report, render_report(cleaned_data, cleared))
)

cleared holds only the findings to act on, with an instruction column: the proposed fix for a TAKE, the reviewer's note for a TWEAK. Log the review once, outside the pipeline: kl_log_verdicts(kl_read_verdicts(kl_newest_verdicts("qa", review = "annual-2026-qa"))).

9. Keep the decision log honest

kl_log_decision("Exclude test records from the intake extract", "approved",
                by = "Your Name", basis = "Test records carry a fixed prefix",
                evidence = "WP-04", assurance = "self-reviewed", ref = "annual-2026")
kl_verify_log()

Each entry carries a fingerprint of the one before it, so an edited, removed or reordered earlier entry is caught. Anything above self-reviewed needs a named second person.

What the chain cannot catch alone, and the fix

Someone could rewrite the whole file, or remove the newest entries. At milestones, such as a report going out, record the head somewhere outside the folder:

kl_log_head()                       # e.g. "14:sha256:9f2c…"
kl_verify_log(expect_head = "14:sha256:9f2c…")

Paste the head into the work papers or an email to a supervisor. One writer at a time: two people appending at once on a shared drive can break the chain.

10. Measure your city's data infrastructure

Pipelines need clean, machine-readable data to point at. The UK's LG Inform Plus, a shared data, standards and benchmarking service for English councils, makes a ready checklist of what that supply can look like: 22 capabilities and 15 recurring design patterns.

cl <- kl_checklist()
kl_uk_terms()                 # UK terms, with the nearest US equivalent
city <- kl_coverage_new("Your City")
  1. Choose your rows: keep the ones your office would act on, such as records retention, statutory mandates, data provenance and open-data access.
  2. Add your own rows for local sources the UK model lacks: rbind() them onto kl_checklist() and pass the result as checklist =.
  3. Rate only what you have checked, with dated evidence: kl_coverage_set(city, id, tool, status, evidence, gap). Unassessed is not the same as missing.
  4. Be fair to the owner: a "missing" is a statement about another agency's system. Say specifically what is absent, and check it with that agency before the matrix leaves your office.
  5. Check, then date: kl_coverage_check(city) before sharing, and recheck yearly.

The method was first worked through in the author's personal DC Inform+ project. The capability structure is drawn from LG Inform Plus public guidance, under the UK's Open Government Licence.

11. Add version control

Git is free, open source and runs on your own machines. GitHub is only one place to host it, and optional.

  1. No server: IT creates a bare repository on the shared drive. Each analyst clones it locally, works there and pushes back. Do not work directly inside a repository on a network drive.
  2. Add the knowledge folder: commit knowledge/ alongside the code.
  3. A server inside the network, once several analysts share a project: Forgejo (GPLv3 or later; trademarks held by the nonprofit Codeberg e.V.) or Gitea (MIT; company-backed by Gitea Ltd, whose subsidiary CommitGo sells a commercial edition). Both work with RStudio's Git pane, and repositories move freely between hosts.

12. Terms used here

Reproducible analytical pipelineCode that takes raw data to the published output with no manual steps.
Knowledge layerThe office's plain-file record of its projects, their connections, who holds them, and what was decided.
Single point of knowledgeWork only one person could run or explain.
FindingAnything a reviewer must rule on before work proceeds.
VerdictTAKE (do the proposed fix), TWEAK (do it the reviewer's way, per the note), MERGE (same as another finding), HOLD (not this pass), DISCUSS (talk first), DROP (no).
Rubber stampAn approval given without a review.
HashA short fingerprint of exact contents; any change gives a different hash.
Bare repositoryA Git repository with no working files, used only for sharing.
